Play around

Eighteen hands-on tasks for the pricing domain. Each one has the setup, the steps and what you should see, with a link back to the doc that explains why. Do them in order the first time: later tasks reuse the data from earlier ones.

Before you start: the tasks are written from the docs, which were read from source and not all run against a store. Where I did not know the exact control panel screen, I give the REST API call instead. If what you see differs from the expected result, that is worth writing down: it is either a gap in the docs or a real difference between two implementations.

Preparation

  • A dev store on the cloud dev VM, with a store hash and an API token that can manage products, price lists and customer groups. The REST calls below use https://api.bigcommerce.com/stores/{store_hash}/v3/... with the X-Auth-Token header.
  • One currency. Use the store's default currency so the exchange rate is 1 and the numbers in the tasks add up.
  • Test data. One product with two variants (S and M, both 50.00), one simple product at 50.00, and three customer groups (Play A, Play B, Play C). The tasks name them where needed.
  • Experiments are per store in LaunchDarkly. Ask for them to be set for your store, or set them in the dev environment:

Caches. After you change setup, results can lag: price list assignments (alternative-pricing-cache), catalog data, store settings and tax settings are cached, and bcapp caches product page responses for 20 seconds. If a number does not change, wait or restart the service before you suspect the code. See Code Structure, 7. Cross-cutting pieces.

1Run the service locally and call the estimate RPCEnvironment✓

Goal. Get the Pricing service running against a dev store and see a real ListEstimatedTaxProductPrices response.

You need

  • A cloud dev VM store (the service reads that store's database)
  • A GitHub token with access to the bigcommerce packages
  • grpcurl or any gRPC client

Steps

  1. In the pricing repo, run cp .env-example .env and fill GITHUB_TOKEN and GITHUB_USER. Dependencies are resolved from GitHub Packages, so the build fails without them.
  2. Start sbt. At the root project run bgRun and choose pricing-rpc at the prompt (the other choice is the event listener).
  3. Read the startup log for the gRPC port. The container config uses 9501. Use bgList to see what is running and bgStop to stop it.
  4. Pick a product ID from your store and call the RPC (protos come from the interfaces repo, and enum values use the proto names such as USD and US):
    grpcurl -plaintext \
  -import-path ~/Projects/interfaces/proto \
  -proto bigcommerce/rpc/pricing/TaxPricingPrototype.proto \
  -d '{
    "store_id": 1234,
    "requested_items": [ { "product_id": 112 } ],
    "currency_code": "USD",
    "customer_group_id": 0,
    "channel_id": 1,
    "currency_decimal_precision": 2,
    "country_code": "US"
  }' \
  localhost:<grpc-port> \
  bigcommerce.rpc.pricing.TaxPricingPrototype/ListEstimatedTaxProductPrices
  5. Optional: run the unit tests with ./script/test, or one module from inside sbt, for example price-lists / test. Functional tests need FUN_TESTS_STORE_ID set in .env.

Expected

  • One product_prices entry for the product, in request order, with tax_entered_as and prices (calculated_price, price and so on, each as as_entered, tax_inclusive, tax_exclusive).
  • Without exchange_rate the service looks the rate up from the currency projection in Redis, and takes the decimals from it when your precision is 0.
  • If startup fails with a Redis error: the service connects to persistence Redis at boot and throws if it cannot. Check the Redis settings in .env.

2Debug a price with the calculation dataEnvironment✓

Goal. See which branch, settings and prices the service used for one item, without attaching a debugger.

You need

  • The service running (task 1)

Steps

  1. Repeat the call from task 1 with "include_calculation_data": true added to the request.
  2. Read the calculation_data field of the response. It is a JSON string, so pipe it through jq or paste it into a formatter.
  3. Find the pricing mode, the price list assignment, the prices after resolving, and the calculation method used for your item.
  4. Change something in the request (add variant_id, then add option_values) and compare which calculation method changes.

Expected

  • calculation_data is filled only when you ask for it, and holds the data, flags and settings used to calculate the prices.
  • A request with only a product ID, a product ID with a variant, and a product with options that resolve to one variant should end in different branches.
  • It is meant for comparing the Pricing service with bcapp. The proto says it is not a stable API.

Reference: Estimate RPC, 1. Request and response · Estimate RPC, 6. The five calculation branches

3Plain catalog price (mode None)Data setup✓

Goal. See what the service returns when nothing replaces or lowers the catalog price.

You need

  • A simple product with price 50.00 and retail price 75.00
  • A customer group with no price list and no discounts (group 0 works)

Steps

  1. Create or edit the product: price 50.00, retail price 75.00, no sale price. Use a store with one currency so the exchange rate is 1.
  2. Call the estimate RPC for the product with customer_group_id: 0.
  3. Add a sale price of 45.00 to the product and call again.

Expected

  • First call: calculated_price 50.00, price 50.00, retail_price 75.00, and saved 25.00 (retail minus calculated).
  • After the sale price: calculated_price 45.00 (the sale applied), sale_price 45.00, price still 50.00, and saved 30.00.
  • If the tax zone for your country_code has no tax, tax_inclusive equals tax_exclusive. One of the two always equals as_entered.
  • If a call shows the old price, wait: catalog data can be cached (catalog-price-data), and so can store settings.

4Option price ruleData setup✓

Goal. Watch a rule change calculated_price and nothing else.

You need

  • A product with a size option and two variants (S at 50.00, M at 50.00)
  • A relative price adjustment of +5.00 on the option value M

Steps

  1. Add the price adjustment to the M option value (the docs call these option set rules and product rules).
  2. Call the estimate RPC with option_values that resolve to variant S, then to variant M.
  3. Call again with only the product ID and note price_range.

Expected

  • S: calculated_price 50.00. M: calculated_price 55.00.
  • price, sale_price and retail_price do not change. Only calculated_price carries the rule.
  • price_range is built from the variants' prices and does not include the rule, so it can disagree with M's calculated_price.

Reference: Estimate RPC, 7. What changes calculated_price · Estimate RPC, 6. The five calculation branches

5Customer group discounts: which one winsData setup✓

Goal. See the order the service picks a discount in, and that it only touches calculated_price.

You need

  • A customer group (call it Play A) with no price list
  • A product with price 50.00 in one category

Steps

  1. Give Play A a 10% discount on all products. Call the estimate RPC with Play A's group ID.
  2. Add a 20% discount on the product's category and call again.
  3. Add a 5% discount on the product itself and call again.
  4. Call once more with customer_group_id: 0.

Expected

  • 10% on everything: calculated_price 45.00.
  • With the category discount added: 40.00. A category discount beats the sitewide one.
  • With the product discount added: 47.50. The product's own discount wins, even though it is the smallest.
  • Group 0: 50.00. price, sale_price and retail_price never change, and the range ends get the discount.
  • The discount is applied after option rules. On variant M of the task 4 product (with its +5.00 rule), the 10% sitewide discount gives (50.00 + 5.00) × 0.9 = 49.50.

Reference: Estimate RPC, 7. What changes calculated_price · Estimate RPC, 4. Which pricing mode applies

6A global price listData setup✓

Goal. See a price list record replace the catalog price, and what happens to a variant with no record.

You need

  • The product from task 4, and customer group Play A from task 5
  • A price list whose tax setting is use global

Steps

  1. Create a price list: POST /v3/pricelists with a name and active: true.
  2. Add a record for variant S: PUT /v3/pricelists/{id}/records with variant_id, currency and price 34.00.
  3. Assign the list to Play A and channel 1: POST /v3/pricelists/assignments.
  4. Call the estimate RPC for Play A with variant S, then variant M.

Expected

  • S: calculated_price 34.00. The record replaces the catalog value, and the group's discounts from task 5 are ignored: a price list and discounts never apply together.
  • M has no record on a global list, so it keeps its catalog price (55.00 with the rule from task 4).
  • tax_entered_as follows the store's setting, because the list is global.
  • Call again for group 0. It should still get catalog prices: only the assigned group sees the list.

Reference: Estimate RPC, 5. What overrides what · Estimate RPC, 4. Which pricing mode applies

7Which pricing mode winsData setup✓

Goal. Check the precedence rules by building three shoppers.

You need

  • Tasks 5 and 6 done
  • Customer groups Play A, Play B and Play C

Steps

  1. Play A already has a price list and discounts. Call the RPC for Play A.
  2. Give Play B discounts only, and assign a second price list to customer group 0 on channel 1 (a channel-wide list). Call for Play B.
  3. Leave Play C with nothing. Call for Play C, and for group 0.
  4. For each call, read the mode from calculation_data (task 2).

Expected

  • Play A: PriceList. A group's own list comes first.
  • Play B: Discounts. The channel-wide list applies only when the group has no discounts.
  • Play C: the channel-wide list (PriceList). Group 0: PriceList too, as the group has no discounts.
  • Remove the channel-wide assignment and Play C falls to None: plain catalog prices.

Reference: Estimate RPC, 4. Which pricing mode applies

8An inclusive or exclusive price listData setup✓

Goal. See that a list with its own tax setting never falls back to catalog prices.

You need

  • The experiment PROJECT-5992.Feature_price_lists_tax_inclusive_exclusive on for your store
  • Catalog v3 enabled on the store

Steps

  1. Create a price list with prices entered exclusive of tax (the setting prices_entered_with_tax, offered when the experiment is on). Add a record for variant S only, and assign it to Play A.
  2. Call the estimate RPC for variant M with enable_null_prices_in_response false, then true.
  3. Check tax_entered_as on the response.

Expected

  • M has no record, so it is not priced from the catalog. With the flag false the prices come back as zero. With it true they come back null.
  • tax_entered_as is ENTERED_EXCLUSIVE, whatever the store's own setting says.
  • If the list shows as global instead, check the experiment: with it off, every list is forced to use global.

9Tax: inclusive and exclusive amountsData setup✓

Goal. Watch tax add amounts without changing the entered price.

You need

  • A tax zone with a 10% rate for your test country, on the product's tax class
  • A plain product with price 50.00

Steps

  1. With the store set to enter prices exclusive of tax, call the estimate RPC for a shopper in that country (country_code) and a customer group with no price list.
  2. Switch the store's catalog setting to enter prices inclusive of tax. Wait for the settings cache to expire, or restart the service, and call again.
  3. Call with a country outside any tax zone.

Expected

  • Exclusive: as_entered 50.00, tax_exclusive 50.00, tax_inclusive 55.00.
  • Inclusive: as_entered 50.00, tax_inclusive 50.00, tax_exclusive 45.45. The same number now means something else.
  • Outside any zone, the store's rest of the world zone is used. If it has no tax, the three amounts are equal.
  • Every price line (price, retail_price, range ends, monetary bulk tiers) gets its own three amounts. saved is computed after tax.

10Bulk pricing tiers in the estimate RPCData setup✓

Goal. See that the estimate returns tiers as data and never applies them.

You need

  • A product with price 50.00

Steps

  1. Add bulk pricing rules to the product: POST /v3/catalog/products/{id}/bulk-pricing-rules, for example 5 or more units at 10% off.
  2. Call the estimate RPC for the product and read bulk_tiers and calculated_price.

Expected

  • bulk_tiers lists the tier with quantity_min 5 and a price_change.
  • calculated_price is still 50.00. The estimate has no quantity, so tiers are only data for the client.
  • A percentage tier has no tax amounts. A monetary tier gets tax_inclusive and tax_exclusive.
  • You will see the tier applied in the cart in task 16.

11Category page price shapesStorefront✓

Goal. Match the three price shapes on a category page to the fields behind them.

You need

  • The flag STRF-14727.Prices_from_gql_for_categories set to the string enable for your store (a literal true does not count)
  • Three products in one category: a plain one, one with a sale price, one with variants at different prices

  • The numbers should match what the estimate RPC returns for the same shopper (task 3).

12Product page: first paint versus option changeStorefront✓

Goal. Find out which service prices which moment on a product page.

You need

  • The flag STRF-14355.Migrate_price_data_to_gql_for_product_details set to enable
  • The product from task 4 (with the +5.00 option rule)

Steps

  1. Open the product page and, in the browser console, read window.BCData.product_attributes.price. This is the first paint, and it comes from the GraphQL price.
  2. Open the network tab, then change the size option.
  3. Find the POST /remote/v1/product-attributes/{productId} request and read data.price in its response.
  4. Compare the two prices for the same selection. Then change the option back and forth quickly.

Expected

  • The first paint is priced through StorefrontGraphQL, which can reach the Pricing service.
  • After an option change the price comes from bcapp, which asks the Pricing service only for the price list and its records and does the maths in PHP. It never calls ListEstimatedTaxProductPrices.
  • The two should match. Where they do not, you have found a difference between the two implementations.
  • Gotchas: bcapp may cache the whole response for 20 seconds, with a key that has no customer group, channel or currency. Quick changes can also arrive out of order, so the last response to arrive wins.

Reference: Understand Client Side, 2. product-attributes · Understand Client Side, 4. Stencil Storefront PDP

14Read a cart line's price fieldsCart and checkout✓

Goal. Match every price field of a checkout line item to its formula.

You need

  • A plain product with price 50.00
  • A way to create a promotion (an automatic 10.00 off the product)

Steps

  1. Create a cart with two units: POST /api/storefront/carts.
  2. Read it back: GET /api/storefront/checkouts/{cartId}, and look at cart.lineItems.physicalItems[0].
  3. Add the 10.00 promotion and read the checkout again.

Expected

  • Without a discount: listPrice 50.00, extendedListPrice 100.00, salePrice equal to listPrice, originalPrice 50.00 and no strike-through.
  • With the promotion (prices entered and displayed exclusive): discountAmount 10.00 for the line, salePrice 45.00, extendedSalePrice 90.00, and comparisonPrice 50.00 (a strike-through).
  • salePrice here is the unit price after discounts, not the catalog sale_price.
  • cart.baseAmount is the cart total before discounts and cart.cartAmount is after them.

Reference: Understand Client Side, Prices in the Storefront Checkout API response · Understand Client Side, 5. Cart / Checkout

15Cart lines priced from a price list, and a line with no priceCart and checkout✓

Goal. See cart pricing go through GetCartPricing, and what happens to a line with no price.

You need

  • Both experiments on for your store: PROJECT-5992 and PROJECT-8948.hydrate_cart_prices_from_pricing_service
  • The exclusive price list from task 8 (a record for S only), assigned to Play A
  • The service running locally (task 1) or deployed

Steps

  1. As a customer in Play A, add variant S and variant M to a cart.
  2. Read the checkout (GET /api/storefront/checkouts/{cartId}).
  3. Turn PROJECT-8948 off, reload the checkout, and compare.
  4. Optional: repeat with an inclusive list, and compare the price you entered with the amounts shown.

Expected

  • Line S is priced from the record. Line M has no record on an exclusive list, so it comes back with no price and bcapp removes it from the cart, silently.
  • With the second experiment off, bcapp prices the cart itself in PHP, with two calls to the Pricing service for the price list and its records. The result should be the same, but the docs have not compared the two paths, so note any difference.
  • Inclusive list: the service never sets prices_entered_tax_inclusive, so bcapp always receives false. Note whether inclusive prices are treated as exclusive. That is an open question in the docs, so write down what you see.

16Cart-wide bulk tierCart and checkout✓

Goal. See that a tier is chosen from quantities summed over the whole cart.

You need

  • The product from task 4 with variants S and M
  • A bulk pricing rule on the product: 5 or more units at 10% off
  • A price list for Play A with a record for S (task 6), and the cart experiments on

Steps

  1. As a customer in group 0 (no price list), add S × 2 and M × 3. Read the line prices from the checkout.
  2. As Play A, with the price list record on S, add the same quantities. Read the line prices again.
  3. Give the record on S its own bulk tiers and repeat.

Expected

  • Group 0: both lines are in the same product, total 5, so both get the 10% tier.
  • Play A: S is priced from its record and uses the record's tiers (none until step 3) with its own quantity of 2. M uses the product's catalog tiers with (2 + 3) − 2 = 3, so M gets no tier.
  • The tier is applied to the price here, unlike in the estimate RPC (task 10).

Reference: GetCartPricing, 5. The bulk tier · GetCartPricing, 9. Compared with the estimate RPC

17Tax display and the strike-throughCart and checkout✓

Goal. See the display side of tax change the checkout fields, and when the strike-through shows.

You need

  • A tax zone with a 10% rate
  • Prices entered exclusive of tax
  • The discount from task 14 on the line

Steps

  1. Set the tax zone to display prices exclusive of tax. Read the line item in the checkout.
  2. Change the zone to display prices inclusive of tax and read it again.
  3. Note isTaxIncluded on the cart, and salePrice, comparisonPrice and discountAmount on the line.

18The event listener cleans up price dataEvents✓

Goal. Run the second process and see a catalog event remove price records.

You need

  • RabbitMQ reachable from your environment (as on the cloud dev VM)
  • A price list record for a throw-away product's variant

Steps

  1. Start the second process: run bgRun at the sbt root and choose the event listener this time.
  2. Create a throw-away product with a variant, add a price list record for the variant, and give the product a customer group discount.
  3. Delete the variant, check the price records for it, then delete the product.
  4. Watch the listener's log. The handler logs each incoming message at debug level, so raise the log level to see them.

Expected

  • The catalog-events queue delivers a variant deleted event. The listener deletes the price records for that variant.
  • A product deleted event deletes the product's price records and its customer group discounts.
  • A category deleted event deletes that category's customer group discounts.
  • Each message is acknowledged after the work finishes, whether it succeeded or failed.
