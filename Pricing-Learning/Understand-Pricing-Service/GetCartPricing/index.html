1. Purpose

The question it answers: what does one unit of each cart line cost, for this line's options, with the quantities in the whole cart, for this customer group, channel and currency?

Who calls itbcapp, from CartPricingServiceClient::getCartPricing, called by PriceAssignmentService::hydrate when the cart projection is built. It is used only when the experiments PROJECT-5992.Feature_price_lists_tax_inclusive_exclusive and PROJECT-8948.hydrate_cart_prices_from_pricing_service are both on. Other callers: none found, not searched exhaustively.
What it replacesbcapp's own cart pricing, where bcapp asked the Pricing service only for the price list and its records and did the maths in PHP. The code comments say the adjustment order is chosen to match how bcapp prices the cart.
What comes backOne price per request line, in request order: price, calculated_price, sale_price, retail_price, map_price and the bulk tier that was applied.
What it does not doNo tax. No rounding. No price ranges or variant lists: it prices the selected variant only. No promotions or coupons, which bcapp applies later. No stock.

Registered in Boot.scala next to the other RPCs: register(CartPricingGrpc.bindService(cartPricingImpl, PricingAsyncThreadPool)).

2. The flow

One request. Loops every 8s.

Step 0Contextcurrency projection: exchange rate, decimals
Step 1Catalog fetchListCatalogPrices, then × exchange rate
Step 2Mode and discountsPriceList, Discounts or None
Step 3Resolve base pricesprice list records override catalog
Step 4Bulk tierquantities summed over the cart
Step 5Adjustrules, tier, discount, picklists
DoneResponserequest order, null if no price

The steps run one after another (a Scala for comprehension in CartPricingService.buildPrices); none run in parallel.

  1. Context. CartPricingImpl turns each request item into a domain item. It looks the currency up in the currency projection by store ID and currency code, which gives the exchange rate and the decimal places, and builds a CartPricingContext.
  2. Catalog fetch. CartCatalogServiceClient makes one ListCatalogPrices call (15 second deadline, read-only database by config) for all items. Per item Catalog returns the selected variant, selected picklists, option set rules, product rules and bulk tiers. Every money value is multiplied by the exchange rate; percentage rules are not. Results are matched back to the request items by product, variant and options. An item Catalog does not return gets empty data. If the whole call fails, every item gets empty data and the RPC still succeeds.
  3. Mode and discounts. The service reads the store's pricing features (one is applyBulkTiersAfterDiscounts) and finds the pricing mode for the customer group and channel. Only in Discounts mode does it load the customer group discounts, for the product IDs of every line and every picklist.
  4. Resolve base prices. In PriceList mode, price records are read for the selected variants and picklist variants, and they replace the catalog prices of those variants. See section 4.
  5. Bulk tier. For each line, one tier is chosen using quantities summed over the whole cart. See section 5.
  6. Adjust. The selected variant's calculated price is adjusted by rules, the tier, customer group discounts and picklists, in an order that depends on where the price came from. See section 6.
  7. Response. Each result becomes a CartSelectionPriceWithNullablePricesProto, in request order. A line with no price comes back with all price fields unset.

4. Mode, price lists and base prices

Pricing mode is found by AlternativePricingProvider.findAlternativePricingForRequest from the customer group and channel, the same way as for the estimate RPC: see which pricing mode applies. The result is PriceList (with a price list ID), Discounts, or None. The service also learns whether the list's prices are entered inclusive or exclusive of tax.

ModeWhat the cart path does
PriceListReads active price records for the selected variants and picklist variants of all lines, in the cart currency, with their bulk tiers. Stale reads are allowed. If the store uses layered price lists, the read returns the layered result. If the read fails, the error is dropped and the records are treated as empty.
DiscountsLoads the customer group discounts for every line's product and every picklist product. No price records.
NoneCatalog prices only.

Resolving a variant's price. This runs for the selected variant and for each picklist variant (resolveVariantPrice, with null prices allowed). Inc/ex price list means the list's prices are entered inclusive or exclusive and the store flag priceListPricesInclusiveExclusiveTax is on.

CaseResult
The variant has a price recordPrice list Every value comes from the record: price, calculated_price, sale_price, retail_price, map_price. Source is PRICE_LIST.
No record, and an inc/ex price listAll five prices are null. Source is PRICE_LIST. The line ends up with no price.
No record, any other caseCatalog The catalog variant prices, converted by the exchange rate. Source is CATALOG.

5. The bulk tier

The tier is chosen with quantities summed over all lines in the request (CartBulkQuantities), not each line's own quantity. A tier matches when quantityMin ≤ quantity and the quantity is within quantityMax, or the tier has no max.

Selected variantTiers usedQuantity matched on
Has a price recordPrice list the record's tiersThe variant's total over the cart
From a price list, no record (inc/ex)NoneNot applicable
Any other variantCatalog the product's catalog tiersThe product's total over the cart, minus units priced from price records
No selected variantNoneNot applicable

Example. Product P has catalog tiers. The cart has variant A × 2, which has a price record, and variant B × 3, which has none. A uses its record tiers with quantity 2. B uses P's catalog tiers with quantity (2 + 3) − 2 = 3, because A's units were priced from records and do not count towards the catalog tier.

6. Adjusting the price

Each line starts from the selected variant's calculated_price: the record's, or catalog's with the sale price already applied. What happens next depends on the source. Pick one:

Where the price came from

    • Rules are the option set rules, then the product rules. Each is a percentage, a relative amount or a fixed price.
    • Customer group discount uses the same selection as the estimate RPC: see what changes calculated_price. It is applied to the product's price and to each picklist's own price.
    • Picklist prices are added to the result. If any picklist price is null, the whole price is null.
    • Floor. The result is floored at 0. A catalog bulk tier is floored on its own as well.
    • Not adjusted: price, sale_price, retail_price, map_price. Only calculated_price changes.
    • No rounding. I found no rounding in the cart path. The exchange rate multiplication and the adjustments keep full decimal precision, and the value is sent as units and nanos.

    8. When a price is null

    A null price means all price fields are unset for that line. bcapp reads it as "no price" and removes the line from the cart.

    CauseWhere
    Catalog returned nothing for the line, or the whole ListCatalogPrices call failedNo selected variant, so the line is null. A Catalog failure does not fail the RPC: every line comes back null.
    The selected variant has no price or no calculated priceFor example an inc/ex price list with no record for the variant.
    A picklist price is null after adjustingFor example a picklist product with no record on an inc/ex list.

    Other failures, such as the currency lookup, surface as RPC errors through ContextualExceptionHandler. I did not test any failure path.
