1. The pipeline

One request. Loops every 8s.

Step 0Contextstore, group, channel, currency, exchange rate
Step 1Catalog fetchListCatalogPrices, then × exchange rate
Step 2Pricing modePriceList, Discounts or None
Step 3Resolve base pricesprice list records override catalog
Step 4Branch + adjustpick prices, then change calculated_price
Step 5Round, tax, savedin-process Tax
DoneResponserequest order
  • Context. If the request has no exchange rate, it is looked up from the currency projection, together with the decimal places.
  • Catalog fetch. One call returns, per item, the base product price, every variant's price, the selected variant, option set and product rules, picklists and bulk tiers. Every money value is multiplied by the exchange rate (percentage rules are not). A flag caches catalog data by product ID, only for items with no variant and no options.
  • Steps 2 and 3 are the next two sections. Steps 4 and 5 follow after them.

2. Which pricing mode applies

Decided from the customer group and channel, by PricingPriceListAssignmentService. The first match wins.

#ConditionMode
1A price list is assigned to the customer group, or to the group and channel (price lists feature on)PriceList
2A channel-wide price list (customer group 0), and the group has no discounts (both features on)PriceList
3The group has customer group discounts (feature on)Discounts
4Anything elseNone, plain catalog prices

So a price list and customer group discounts never apply together. A channel-wide price list loses to the group's discounts. The result is cached per store, group and channel.

4. The five calculation branches

After the base prices are resolved, each item takes exactly one branch. The branch depends on what catalog returned and on store settings. It decides where every response field comes from. Pick one:

Branch
BranchMethodWhen
noPurchasableVariantnoPurchasableVariantCatalog returned no selected variant and no variants. Also what a missing item looks like.
singleSelectedVariantPricesingleSelectedVariantPriceA selected variant, no variant list. This is a request with a product ID and a variant ID.
singleSelectedVariantPriceAndRangesingleSelectedVariantPriceAndRangeThe options fully resolve to one variant, and other variants exist.
partial selectiontoOverviewPriceWithRangesForPartialSelectionsThe options do not resolve to a variant, and the store prices that from the base product (partialSelectionLowestVariantPrice off with options, or productOverviewUseLowestVariantPrice off with pre-selected options). Skipped on an inc/ex price list.
no selectiontoOverviewPriceWithRangesEverything else. This is the usual product listing case.
  • Base product in the range. The base price joins the min and max candidates only when the product has no required options and productOverviewUseLowestVariantPrice is off.
  • Ties. The cheapest variant is sorted on calculated_price at currency precision, then on retail price, to match bcapp.
  • Null prices. When a calculated price is null (or becomes null after adjusting), the item gets an empty price, not zero. Zero prices come from a missing selected variant.
  • retail_price_range is built from the variants whose retail price is above their calculated price. It is empty when the min and max are equal.
  • Bulk tiers. The selected variant's price record tiers if there is one, otherwise catalog's. They are dropped if any variant came from a price list. They are returned as data and never change calculated_price.

5. What changes calculated_price

adjustPrice runs these in order, on the price the branch picked:

  1. Option set rules: percentage, relative or fixed.
  2. Product rules: percentage, relative or fixed.
  3. Customer group discount, Discounts mode only. Product discount wins. Without one, the lowest category discount (if it beats the price). Without one, the sitewide discount. Methods: percent off, price off (× exchange rate), fixed price, and the two markup methods (flag-gated).
  4. Picklist prices are added. If any picklist price is null, the result is null.
  5. Floor at 0.
Easy to miss: the price range min and max get customer group discounts, but not option rules or picklists. A code comment says this matches bcapp. So the range can disagree with calculated_price when rules apply.

6. To the final response

  1. Round every price to the currency's decimal places, before tax.
  2. Resolve "entered as" per item: the price list's inc or ex flag, or the global tax catalog setting.
  3. Tax. The in-process Tax RPC prices calculated, price, sale, retail, MAP, both range ends, and monetary bulk tiers. Each becomes { as_entered, inc_tax, ex_tax }. If the tax call fails, it is logged and each price falls back to inc = ex = the as-entered amount.
  4. saved is computed last, only when retail is greater than calculated: retail − calculated, for all three amounts.
  5. Order. The response is put back in request order and bulk tiers are sorted by minimum quantity. An item with no result comes back with a null calculated_price.

The response is ListEstimatedTaxPricesRespProto(prices, calculation logs). The logs are filled only when the request sets include_calculation_data.
