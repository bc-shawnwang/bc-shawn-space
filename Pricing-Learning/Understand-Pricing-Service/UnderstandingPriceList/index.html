1. Global versus inclusive or exclusive price lists

Every price list has a prices entered with tax setting. It has three real values, and a fourth that means "not set":

ValueStored asMeaning
USE_GLOBAL1Follow the store's catalog setting for whether prices include tax.
ENTERED_INCLUSIVE2This list's prices include tax.
ENTERED_EXCLUSIVE3This list's prices exclude tax.
UNKNOWN0Not set. On create with the inc/ex flag on, it becomes USE_GLOBAL.

The setting is stored on the price list. The assignment lookup joins it in (price_lists.prices_entered_with_tax) and returns it with the list ID, so pricing knows how to read prices before it fetches any record.

How the two behave differently

Use globalInclusive or exclusive
Who decidesThe store's catalog setting pricesEnteredTaxInclusive, read at request time (store config, cached).The list itself.
Variant with no recordFalls back to its catalog price, so a list can cover only some variants.No fallback: null prices (zero in the estimate RPC unless enable_null_prices_in_response).
Picklist with no recordUses its catalog price.The whole price is null.
Cart (GetCartPricing)Same catalog fallback.No price, so bcapp removes the cart line.
Base product priceUsed for partial selections.Never used: the partial-selection branch is skipped.
Tax stepThe store setting says how the amount is read.The list's setting says how the amount is read.
If the store setting changesWhat every global list's numbers mean changes, with no data change.No effect: the list keeps its own setting.
Cascading layersLayers must have the same value as the primary list.Same. See section 2.

Flags and requirements

  • Per-store switch. The flag PROJECT-5992.Feature_price_lists_tax_inclusive_exclusive gates inclusive and exclusive lists. With it off, create and update calls force every list to USE_GLOBAL, and pricing treats every list as global.
  • Catalog v3. Creating or updating a list to inclusive or exclusive needs the store's catalog v3 setting on. USE_GLOBAL is always allowed.
  • Mode matters too. A price list is only one of the three pricing modes. With discounts or with no list at all, the store's global setting applies.

What it means in practice

  • The same number reads differently. With a 10% rate, 44.00 entered exclusive gives 48.40 inclusive. Entered inclusive, it gives 40.00 exclusive. The tax calculator in Understanding tax shows both.
  • An inclusive or exclusive list needs a record for every variant the group can buy. A missing record means no price, not a catalog price. On the storefront that product has no price, and in the cart the line is removed.
  • A global list is forgiving but moves with the store. A partial list works, because the rest falls back to the catalog. But if the merchant flips the store's setting, every global list's prices are read the other way.
  • An inclusive or exclusive list is explicit. It is the right choice when one store has lists entered differently, for example a trade list entered exclusive next to retail prices entered inclusive.
  • It limits layering. Lists can only be layered with lists of the same value, and the value is locked while a list is in a layer relationship.

2. Cascading price lists and layers

A price list can have other price lists behind it as fallback sources of records. This section covers what that means, how a read walks them, and how they are set up.

2.1 The concepts

TermMeaning
Price listA named set of price records, assigned to a customer group and channel. It has an active flag and a "prices entered with tax" setting.
Price recordOne price for one variant in one currency in one list, with optional sale, retail, MAP and bulk tiers.
Primary listThe list assigned to the shopper's context. It is the one whose layers are read.
LayerAnother price list attached to a primary list, with a priority. It is a fallback source of records, not a copy.
CascadingResolving each variant's record across the primary list and then its layers, instead of from the primary list alone.
Fallback modeA store-wide setting: Priority order (the first list with a record wins) or Lowest price (the cheapest record wins).

Why it exists. The beta developer docs describe it as a way to avoid duplicating a whole price list for a small variation: keep one shared base list and assign it as a fallback layer to several primary lists.

The order records are looked up in. Loops every 8s.

InputShopper contextchannel and customer group
Step 1Assignmentfinds the primary list
Step 2Primary listits record, if any
Step 3Layersin priority order
LastCatalog priceonly if no list has one

The last step depends on the list's tax setting. On a global list a variant with no record anywhere gets its catalog price. On an inclusive or exclusive list it gets no price. See section 2.8.

2.2 How a read cascades

Cascading is applied inside PriceRecordsService.listPriceRecordsNoCount. In order:

  1. Check the conditions. The store's flag PROJECT-7275.enable_cascading_price_lists is on, and the request names exactly one price list ID. Otherwise it reads that one list the normal way.
  2. Get the layers. getLayersForPriceList returns the layer list IDs sorted by priority. It is active layers only unless the request's active filter says otherwise. With the flag off it returns none.
  3. Read all lists at once. One query for the primary ID plus the layer IDs, with the page limit multiplied by the number of lists.
  4. Pick one record per variant and currency (cascadeRecords). The candidates are the records for that variant and currency, in the order primary, layer 1, layer 2, and so on. The store's fallback mode chooses.
Fallback modeChosen record
Priority (the default)The first candidate. The primary list beats its layers.
Lowest priceThe candidate with the lowest calculated price, or the price when there is no calculated price.

The fallback mode is a store-wide setting read from Storefront Config (PriceListFallbackSetting), not a property of a price list. The chosen record is used whole: its price, sale, retail, MAP and bulk tiers all come from the same list.

2.6 How layers are stored

One table in the store database, price_list_layers:

Column or keyMeaning
primary_price_list_idThe list that owns the layers.
price_list_idThe list used as a layer.
priority1 for the first layer, up to the number of layers.
unique (primary, priority)A primary list cannot have two layers at one priority.
unique (primary, price_list_id)A list cannot be a layer of the same primary twice.
  • Writing. Setting layers deletes the primary list's existing layer rows and inserts the new ones, with priority equal to the position in the array plus one. A delete action only deletes. Both are no-ops when the flag is off.
  • Deleting a price list also removes every layer row it takes part in, as primary or as layer (deleteAllLayersWithPriceLists).
  • Flag off. Layers are not read and not written, but rows already in the table stay.

2.7 Rules and limits

RuleWhere and how
Maximum number of layersThe service reads price-list-max-layers: 5 by default in application.conf, overridable with PRICE_LIST_MAX_LAYERS, and set to 1 in the functional test configs. The beta docs say one layer per list. The production value is not known to me. Over the limit: PriceListLayerLimitExceeded.
No self referenceA list cannot be its own layer.
No duplicatesThe same layer ID twice is rejected.
Layers must existAn unknown price list ID is rejected.
Same tax settingEvery layer must have the same "prices entered with tax" value as the primary list, or the call is rejected (PriceListLayerTaxMismatch, a 422 in the beta docs).
Tax setting is lockedYou cannot change a list's tax setting while it is part of any layer relationship, as primary or layer (PriceListTaxChangeBlockedByLayers). Remove the relationships first.
Inactive listsAn inactive list can be assigned as a layer, but a read skips it. The docs say the primary list must be active for its layers to be read.

The layer checks run on create and update in PriceListsService, but only when the flag is on. The check that blocks a tax change is not flag-gated: a code comment says stale layer rows from an earlier time the flag was on could otherwise be ignored, and turning the flag back on would silently give layers with mismatched tax settings.

2.8 Layers and tax settings

  • Same setting across the chain. Because every layer has the primary's value, a cascaded record is always read the same way (inclusive or exclusive or global). The tax step never has to mix them.
  • No record anywhere. A variant is only treated as missing after the primary list and all its active layers have been tried. Then a global list falls back to the catalog price, and an inclusive or exclusive list gives no price. See section 1.
  • The reason for the lock. Changing a list from exclusive to inclusive changes what all its numbers mean. If it were a layer under a primary list with the old setting, the same cascade would mix two meanings, so the change is blocked.
