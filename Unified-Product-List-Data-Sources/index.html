Unified Product List: where each column's data comes from

v3/catalog/products (REST) is the engine behind the ng-products Unified Product List table — it drives sorting, filtering, and pagination. GraphQL is only used afterward, to enrich rows whose IDs are already known.

v3/catalog/products drives sort, filter, pagination, and every base column for every row on the page.
Once row ids are known, a second GraphQL call batches inventory fields onto those same rows — it never filters or sorts them.

Why new backorder filters must live on v3/catalog/products — not on GetProductsInventory GraphQL or any other API

  • The GraphQL inventory query can only look up rows you already know. GetProductsInventory takes filters: { ids: $productIds } — it has no way to ask "which products have a backorder limit over 10" across the whole catalog. It's a resolver keyed on IDs, not a search/filter query.
  • The one filter/sort/pagination pipeline lives entirely on the REST side. Every filter pill — category, channel, price, visibility, and now backorder message — is a query-string operator (:in, :not_in, :min, :max) parsed by useFilters and forwarded as-is to v3/catalog/products by useProducts. Filters combine with AND on that single server-side call, and the same call returns the paginated page. Splitting one filter off onto a different API would mean either fetching the whole catalog client-side to filter it in the browser (breaks pagination and performance) or running two separate paginated queries and trying to intersect their results (breaks correctness of "page 2 of 15").
  • This is exactly what the recent backorder message id commits did. The filter itself (backorder_message_id:in / :not_in) was added straight into supportedFilterPills in useFilters.ts so it flows through the existing v3 REST pipeline like every other filter:
ng-products/src/app-next/apps/ProductList/components/ProductSearch/components/ProductFilters/hooks/useFilters.tsexport const supportedFilterPills = [
  + 'backorder_message_id:in',
  + 'backorder_message_id:not_in',
  'channel_ids:in',
  ...
];
  • A new GraphQL query was added — but only to power the filter's dropdown, not the filtering itself. GetBackorderMessages (backed by a new StoreInventory.backorderMessages(filters: { messageIds, names }) schema field) resolves backorder message names for the picker UI and for labeling already-applied filter pills. The actual "narrow the product list down to these messages" work still happens as a REST query param, because that's the only place server-side filtering of the product collection exists.
  • This isn't specific to inventory data — any future filter or sort field faces the same constraint. Whether it's a backorder limit range, qty backordered, or some attribute that doesn't exist yet, adding it as something users can filter or sort the list by means adding a new query parameter to v3/catalog/products itself — extending the REST schema, the same way backorder_message_id was. GraphQL queries like GetProductsInventory and GetBackorderMessages can only ever enrich or label rows by ID; their schemas have no filter/sort arguments to extend, and the UI's entire filter/sort/pagination pipeline is wired to the REST endpoint alone.
