bc-shawn-space

How a small change causes the issue under problematic in-memory cache design

InternalApiCheckoutService::$quote, StorefrontCartService::$cachedQuote and CartProjectionCache::$cart are three independent request-lifetime caches of “the cart.” They normally converge on the same object by accident of call order. An extra save introduced by the Backorder 1.1 stock-allocation path breaks that accident — Klarna's payForOrder ends up reading a cart copy that never received the order id/token.

Root cause. The underlying design is what's fragile here, not the Backorder 1.1 change itself. The same quote aggregate is replicated across three independent in-memory caches with no defined consistency boundary between them — each service is free to hold, read, and mutate its own copy without any mechanism to keep the others in sync. Once the same logical object exists as multiple separate in-memory copies, an update to one instance can silently leave the others stale, and whether that staleness ever surfaces depends entirely on incidental call order within a request. Today that call order happens to work out: StorefrontCartService populates its cache after the only save in the request, so all three converge on the same object by coincidence, not by design. Backorder 1.1 doesn't introduce a new class of bug — it simply adds one more save into that same request, which is enough to flip the coincidence the other way: StorefrontCartService now populates its cache before the order-linking mutation happens, so it ends up holding a freshly-rebuilt object (“CartInstance2”) instead of the one (“CartInstance1”) that later receives the order id/token. Backorder 1.1 is the trigger; the pre-existing lack of a single, consistent access path for the cart is the actual defect.

Fix direction

  • Quick patch. This is the short-term fix already shipped as BACK-874 (SAVE_QUOTE_VIA_STOREFRONT_CART_SERVICE_ON_ORDER_CREATION): route the final order save through StorefrontCartService::save() instead of CartService::save(). That call re-seeds StorefrontCartService::$cachedQuote with the order-linked quote as a side effect, forcibly re-syncing StorefrontCartService and CartProjectionCache's in-memory copies right before Klarna reads them. It closes this specific gap but doesn't address the underlying design — the next save added anywhere in the request can reopen the same class of bug.
  • Root fix. Reduce the number of independent in-memory copies of the same quote and give the request a single authoritative access path for it, instead of letting each service keep its own mutable cache that can silently diverge from the others. The performance benefit of caching is still worth keeping — it just shouldn't come from handing out separate mutable copies of the aggregate. An immutable read model (or a single owned instance that every layer reads through) preserves the speed of an in-memory cache without recreating the “which copy is the real one” problem every time a new save gets added to the request.
