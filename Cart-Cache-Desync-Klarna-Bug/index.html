bc-shawn-space

Three in-memory cart caches drift apart when Backorder 1.1 is on

InternalApiCheckoutService::$quote, StorefrontCartService::$cachedQuote and CartProjectionCache::$cart are three independent request-lifetime caches of “the cart.” They normally converge on the same object by accident of call order. An extra save introduced by the Backorder 1.1 stock-allocation path breaks that accident — Klarna's payForOrder ends up reading a cart copy that never received the order id/token.

Entry point \Services\Checkout\InternalApiCheckoutService::createOrder() · POST /orders
Trigger flag InventoryExperiments::BACKORDERS_PHASE_1_1_CONTROL_MESSAGING_ON_STOREFRONT
Verified against current bigcommerce/bigcommerce checkout, storefront cart, and payment-provider code
✓ three independent caches — confirmed ✓ Backorder 1.1 inserts extra save — confirmed ✓ Klarna reuses cached quote in payForOrder — confirmed
Root cause. CartProjectionCache::save() nulls its own in-memory $cart after persisting, but nothing tells StorefrontCartService::$cachedQuote or InternalApiCheckoutService::$quote that the object they're holding is now stale relative to Redis. Normally that's harmless because StorefrontCartService happens to populate its cache after the only save in the request, so it converges with everyone else. Backorder 1.1 adds a stock-allocation save before that population point — so StorefrontCartService ends up caching a freshly-rebuilt object (“CartInstance2”) instead of the one (“CartInstance1”) that later gets the order id/token written onto it.

What determines whether this actually fires

  • Requires Backorder 1.1 ON (BACKORDERS_PHASE_1_1_CONTROL_MESSAGING_ON_STOREFRONT) — adds the extra invalidating save between beforeAction and the Klarna provider check.
  • Needs checking per-store in LaunchDarkly to confirm this is live for a given affected store, not just theoretically possible.

Fix direction

  • Stop treating three separate in-process caches as if they were one source of truth for the duration of a request — either invalidate all three together on any save, or have StorefrontCartService/InternalApiCheckoutService always resolve through CartProjectionCache instead of keeping their own copies.
  • Re-seed StorefrontCartService::$cachedQuote with the order-linked quote immediately after the order-creation mutation, so any later fetchQuote() call (Klarna's payForOrder included) sees the up-to-date object.
  • Add a regression test with Backorder 1.1 ON that asserts the quote passed into payForOrder carries the order id/token.
